# Changelog

All notable changes to this project are documented in this file. Entries are
added only when the corresponding PR is merged to `main`.

## Unreleased

- **Spec decision 164:** `vibe manifest` is the official build command (release by default, `--dev` for development); `vibe build` is deferred to vNext. Removed stand-in wording.
- **Empty LLM settings:** Interactive setup and the `.env` loader treat empty or whitespace-only LLM/OpenAI values as unset. Later non-empty lines win, and empty process variables do not block `.env` values; existing file content is preserved.
- **CLI help:** Describes interactive `vibe`; removed `vibe new` points to `vibe`. Manifest help describes unsigned release output, workflow Sigstore signing and the local dev key.
- **Interactive setup (decision 157):** Fill only missing `.env` keys, preserve existing values, avoid duplicates, and prompt only for missing keys.
- **Structured Limits errors (decision 163):** Conflicts name the field, source and resolved values, and explain how to pin the value in frontmatter or delete the Limits line.

- **Limits pins:** API feature frontmatter supports timeout, body and provider. Timeout/body resolve pins → version defaults → definition defaults → built-ins; provider resolves pin → definition provider default → main. Compile, validate and interactive generation check values; prose limits are ignored and prompts explain frontmatter pins. Body sizes accept case-insensitive b/kb/mb units everywhere; previously a lowercase value such as `64kb` built a manifest with a zero body limit.
- **Breaking: structured Limits:** Structured API features now use the same canonical Limits and path.slug rules. Conflicting source Limits fail compile; move those values into frontmatter or remove them.
- **Compile prompt version:** Bumped to prompt-5 (locks recompile). Every compile prompt, guide or example change must bump PROMPT_VERSION; a recorded SHA-256 test guards the rule.
- **Spec decisions:** Assigned decision numbers 150–162 in spec section 0.14.
- **Interactive naming:** Prompts request simple lowercase kebab-case names and default hello world to hello/v1/hello.

- **Breaking: api step op `transform` removed:** Validate rejects `op: transform` in api feature `## Steps`, telling you to delete the step and use `## Transform` (`- in:` / `- out:`). Pre-1.0, no deprecation period; the compile prompt no longer offers it.
- **Deterministic api feature locks:** Natural-language sources ignore model output for Limits and Request `path.slug` rows. Limits always writes provider, timeout and body from source pins/inherited defaults; slug routes get one canonical first `path.slug` row, and other routes drop it.

- **Undefined variable roots (#284):** Validate rejects undefined expression roots, naming the root, location and sorted allowed roots.
- **Compile validation (#288):** Each LLM lock is validated after normalization and repaired with exact validate feedback within the existing shared retry bound. Prompts clarify API steps, expressions and routes. Compilation validates the whole project before writing locks or a build record, and fails without writing either if invalid.

- **Interactive CLI:** `vibe` sets up LLM settings and generates feature sources from natural language, with confirmation and no overwrites.
- **Missing API sources:** Compile errors show the missing `_definition.md` / `_version.md` path, minimal content, and a hint to run `vibe` (interactive).
- **Memory development slugs:** `serve --memory` in development defaults to slug `dev` (tenant `devtenant`) even when other slugs are configured and reloads changed slug files without restart. Other serving modes are unchanged.

- **API expressions:** Support JSON string/number literals, reserved true/false/null words and quoted object keys (no arrays). API `respond value` evaluates expressions; empty or `transform.out` evaluates Transform out, with failures returning 500 INTERNAL without fallback. Missing or `(none)` Transform defaults to in = {} and out = result, including `- in: (none)` / `- out: (none)`. Validation and manifest building reject statically failing expressions and empty Transform bullets.

- **Refresh rotation upgrade:** Run `vibe migrate` before `vibe serve` after upgrading. Reservation columns are added per tenant by migration. A request presenting a token while an earlier request for it is in progress returns a retryable 503 `TX_CONFLICT` without clearing cookies; after it completes, a presentation within the 10-second grace window follows the grace rule, and later presentations are treated as reuse and revoke the family; database/pool timeouts return 504 `TX_TIMEOUT`. Reservations without a committed child are cleared, leaving the presented token current and allowing a retry.

- **LLM error details:** Error messages show provider error codes, Responses API incomplete reasons and expected/reported model names only when they are known allowlisted values; other values appear as `unknown`. Provider message text and response bodies are still never shown.

### Added

- **Spec: challenge request digest (#156, decision 140):** Spec v1.8 section 7.2b defines binding each Turnstile token to a request digest carried in `cdata` (SHA-256 over method, normalized path, normalized query, `Content-Type`, `If-Match` and the raw body hash; server recomputes and compares, failing closed with 403 `CHALLENGE_FAILED`). Confirmed by the PM on 2026-10-16 (full-length digest, login routes included, client IP not covered; per-request `X-Vibe-Request-Nonce` from a CSPRNG so the provider only sees an unreversible digest; raw `+` in the query is invalid; nonces are unique per tenant, one record per request; a nonce record over the D137 cap gives 403 `CHALLENGE_FAILED`, over a D134 capacity cap gives 429 `CHALLENGE_RATE_LIMITED` with `Retry-After` exactly as D134, and every verification failure including nonce reuse gives 403; fixed check order: format, reuse, D137, D134 (superseded by #258: the order now includes the store-unavailable 503, see the #258 entry); `Retry-After` uses the tenant's own oldest record, or its oldest record in that prefix, at most 360 s, 60 s fallback; residual risks tracked in #255 and #256); not yet implemented. Adds `scripts/request-digest-vectors.mjs` with test vectors.

- **Spec: challenge check order (#258):** Spec v1.8 sections 7.2a and 7.2b fix the replay-store check order: format/canonical errors (403), store unavailable (503, fail closed), reuse (403), D137 cap (403), D134 caps (429). The nonce and token records are reserved in one transaction (nonce first, full rollback on failure), and both count toward the caps (2 per request; values reviewed in #256). Every 429 is identical apart from `Retry-After`. Adds tests C10–C12 and T1–T9. PM-approved 2026-10-16 12:44 HKT; not yet implemented.

- **Dependency / advisory CI (#192):** `cargo deny check` (advisories, licenses, bans, sources) runs on pull requests, pushes to main, a daily schedule, and `workflow_dispatch` via `.github/workflows/cargo-deny.yml` (Refs #196).

- **Compile format repair (#92):** When LLM output for a natural-language source fails the lock format check, `vibe compile` re-prompts the model with the validator errors (by line number and fixed message) up to `LLM_FORMAT_RETRIES` times (0–5, default 2) instead of failing the source on the first malformed answer.

- **Raw LLM output dump (#92):** Set `VIBE_DUMP_LLM=1` to save the raw response of every attempt that fails the format check to `.vibe/llm-dump/<source>.attempt-<n>.txt`. Only the response is stored (no prompt); the API key is redacted.

- **LLM budget (#92, from #93):** `LLM_MAX_CALLS_PER_SOURCE` (default 8) and `LLM_MAX_CALLS_PER_RUN` (default 200) bound LLM calls for every adapter, including repair attempts. Config may lower the limits; raising is capped at 2x the default. Invalid values fail.

- **Run lock (#92, from #93):** Only one `vibe compile` writes locks for a project at a time.

- **Challenge replay store (#157):** Challenge single-use state, quotas and capacity live in PostgreSQL in each tenant's own schema (`t_<tenant>.vibe_challenge_replay`, created by that tenant's `vibe migrate`, FORCE RLS) so they hold across instances. The runtime role has SELECT and INSERT only; expired rows are ignored and removed by `vibe migrate`. Capacity is per tenant and client IPs are stored as a per-tenant HMAC. In production with a verifier configured the PostgreSQL store is always used; `vibe serve` refuses to start if a tenant's table is missing or has wrong grants, or if `VIBE_CHALLENGE_REPLAY_STORE=memory` is set. Outside production the store must be chosen explicitly (`memory` or `postgres`). Store errors fail closed (503).

### Fixed

- **Compile auth removal (#92):** Disabled auth in API source frontmatter deterministically replaces inherited or model-emitted auth with `-auth`. Recognized Chinese and English auth-removal phrases count as direct negation without ambiguity warnings; login requirements still conflict with disabled auth, and double negations retain strict checks.

- **Compile validation and LLM handling (#92):** Security checks use original Chinese and English prose, retain ambiguous requirements with confirmation warnings, validate Markdown fences, and report structured declaration conflicts (PM decision 2026-10-16, supersedes #37 English-only rules); translations cannot supply support. LLM dumps redact decoded secrets, multi-line values, credential-bearing URLs, private keys, tokens and authorization headers, preserve directory permissions, and refuse symbolic links. `LLM_FORMAT_RETRIES` accepts only ASCII digits within its supported range. Calls without an explicit LLM budget share an environment-configured counter. The direct `libc` dependency is restricted to Unix targets.

- **Local LLM endpoints:** Private-host opt-in also covers DNS answers from fake-IP proxies. Development serve warns and strips all LLM/OpenAI environment variables, including project `.env` values, before runtime startup; other environments still refuse them. Diagnostics omit keys, request headers and response body text. Transport errors include masked causes, requests send a SDK User-Agent, and non-JSON authorization failures identify possible proxy blocks. `validate --deploy --dev` and `manifest --dev` support local testing of private-endpoint locks; signed dev manifests are refused outside development. Structured locks use deterministic compiler stamps.

- **Refresh 家族限流（決定 147，文件更新）：** 超過上限會要求重新登入。

- **EC signing keys checked at load (#257):** ES256 private keys (PEM and DER) are now checked when they are loaded: PKCS#8 and SEC1 PEMs (PKCS#8 for DER) must name P-256, included public points must lie on the curve, the encoding must cover the input exactly (no trailing data) and the private scalar must be in `1..n-1`. Such keys are refused at startup instead of being accepted or failing at the first signature.

- **Postgres TLS (#174):** `TlsMode::Require` (`sslmode=require`) previously did not enable TLS for database connections. It now requires TLS and fails to connect if the server does not offer it. `sslrootcert` is honored, and an unreadable or empty `sslrootcert` file is reported as an error.

### Breaking

- **Release builds and deploy gate (spec v1.8):** Locks are build output and are not committed (`*.lock.md` is gitignored). `vibe manifest --release` compiles every source in memory (lock files on disk are never read), validates the result, never reads the project `.env`, sends the LLM key only to an allowlisted host (the default `api.openai.com` included), uses no signing key, and writes an unsigned manifest (with `--release-version`, default from a `v*` `GITHUB_REF_NAME`, and the full commit) that the release workflow signs with Sigstore keyless (decision 119). High-risk items are listed in the deploy report and do not block (decision 90 withdrawn; `--release-approval` removed). The manifest records the build mode, version, commit, per-lock `lock_sha256` / content / source / compiler hashes, and all security items. Outside development, `serve` and `migrate` require the Sigstore bundle and `VIBE_RELEASE_VERSION`, check the certificate identity equals exactly `https://github.com/vibe-backend/sdk/.github/workflows/release.yml@refs/tags/v<version>`, the issuer `https://token.actions.githubusercontent.com`, the commit, a GitHub-hosted runner and Rekor inclusion, and verify offline with `cosign` against the compiled-in Sigstore trust root; `VIBE_RELEASE_SIGNING_KEY`, `VIBE_RELEASE_PUBKEY` and `VIBE_MANIFEST_PUBKEY` are gone, and `.vibe/signing.pub` is ignored. `vibe compile` reads `.env` only in development. `vibe manifest` without `--dev` builds a release manifest (same as `--release`); `--dev` automatically creates the local key (mode 0600) on first use, while `vibe keygen` remains optional. `vibe compile --check` now builds in memory and runs the deploy policy instead of comparing with locks on disk. A reference workflow with attestation and `gh attestation verify` is in `docs/ci/`.

- **Deploy policy:** Deploy validation checks every dependency hash, requires locks to match `.vibe/build-record.json` written by `vibe compile`, recompiles structured sources, parses non-migration SQL with an allowlist parser (`UPDATE`/`DELETE` need a non-trivial `WHERE`), refuses feature locks that drop or widen inherited auth roles.

- **Lock approval removed (spec v1.8):** `vibe approve` exits with a removal message accepting old arguments, and locks no longer carry `status`, `approval-mode`, `approved-by`, `approved-at`, `approval-ref`, `approved-commit` or `signature`, nor a per-item `approved-by` under `security-items`. Older locks that still have these fields get one warning per file and the fields are ignored; recompile to drop them. `vibe validate` no longer takes a verify key. Review moves to pull requests. The local flow is `vibe compile` → `vibe validate` → `vibe validate --deploy --dev` → `vibe manifest --dev`, without approval.

- **Read-only refresh `sign-method` (#270, decision 149, PM-approved 2026-10-17 09:36 HKT):** The method named by `token-refresh` `sign-method` must be read-only, including any method it calls through `op: method` at any depth (the platform's `issue-refresh` write is not counted, so the same method still works for login). `vibe validate`, the build and `vibe serve` reject a sign-method that writes with `REFRESH_SIGN_METHOD_WRITES`, naming the lock file, the method and step that write, and the fix. On the refresh path every DB statement of the sign-method also runs READ ONLY; a violation returns a non-retryable 500 `INTERNAL` and leaves the presented token current. The platform records the last refresh time per family in a new `_platform_refresh_families.last_refreshed_at` column, written inside the rotation-confirm transaction (also on a grace reissue); plus a family-level `revoked_at` set in the same transaction as any whole-family revocation; the runtime role may UPDATE only those two columns, and a guard trigger keeps `last_refreshed_at` forward-only, makes `revoked_at` one-way (NULL to a value only), and freezes `last_refreshed_at` once the family row's `revoked_at` is set (a grace reissue revokes only the lost child and does not freeze it). `_platform_refresh_tokens` grants are unchanged. **Upgrade order:** after upgrading, run `vibe migrate` for every tenant (it creates `_platform_refresh_families`, its grants and trigger, and backfills existing families, including `revoked_at` from non-`grace-reissue` token revocations) before `vibe serve`; `vibe serve` refuses to start until it has. Migration: drop sign-method writes of the last refresh time (use `last_refreshed_at`); move other business writes into a normal write method that the client calls after a successful refresh (example in spec §4A.1c, tested as fixture `tests/fixtures/refresh-session`); set `writes: false` in `## Signature` and recompile. Spec v1.8 sections 0.13 and 4A.1c; not yet implemented. Option B is deferred to vNext.

- **Refresh tokens (#95):** `reuse-grace` is tightened from accepting up to 60s to a maximum of 10s (default 10s, spec §4A.1). Configs above 10s (and 0) now fail `vibe validate` and the build, and `vibe serve` refuses to start with a manifest that carries one; set `reuse-grace` to 10s or less and recompile.

- **JWT key policy (D139, #222 #224 #225 #226):** `vibe serve` refuses to start when an RS256 `sign-jwt` signing key or an RSA `VIBE_JWT_PUBLIC_KEY_PEM` is under 2048 bits, when an ES256 signing key or `VIBE_JWT_PUBLIC_KEY_PEM` is not a P-256 key (or its private scalar is outside `1..n-1`, or its encoding has trailing data), or when `VIBE_JWT_PUBLIC_KEY_PEM` does not match `VIBE_JWT_ALG` (these checks run in `vibe serve`, not `vibe validate --deploy`). JWKS keys are filtered by the configured alg (`VIBE_JWT_ALG`, default ES256) at parse time, and a kid that appears more than once in a JWKS is ignored; RS256 JWKS deployments must set `VIBE_JWT_ALG=RS256`. `sign-jwt` without `alg` now defaults to ES256.

- **Strict `writes` and `status` (#166):** In method and API locks, `writes` must be exactly `true` or `false` and `status` a plain HTTP status (100-599); unknown, empty, malformed or repeated values are build and validation errors instead of silent defaults. A step marked `writes: true` must have SQL that writes, a writing step must be marked, and the Signature `writes` must match the steps.

- **Inherited writes through `op: method` (#166):** A method that calls a writing method via `op: method` (at any depth) is now a writing method. Existing manifests where such a method does not declare `writes: true` in `## Signature` now fail build and validation. An `op: method` step may be marked `writes: true` only when its target writes. Security risk grading follows the called methods, and an unknown or malformed `op: method` target is graded as a write (see docs/spec-v1.8.md §10.8).

- **Unverified challenges (#199):** Challenges are verified only on public routes with `when: always`. In production, `vibe serve` and `vibe validate --deploy` now refuse routes that declare a challenge with `when: after-failures` (such as login routes) or on a non-public (authenticated) route, since those challenges are not verified yet. This is temporarily unsupported until verified challenges on these routes are implemented (#201). Development and CI still accept them.

- **Frontmatter declaration (#92, D16):** Structured sources must declare their frontmatter explicitly; the declaration is now required. Malformed name lists are errors, not empty lists.

- **Challenge verification (#118):** `x-challenge-proof` is no longer accepted just because it is non-empty. Routes with `challenge: { type: captcha, when: always }` verify the token with Cloudflare Turnstile siteverify (hostname and action checked, each token single-use) and fail closed (403 `CHALLENGE_FAILED`, 503 `CHALLENGE_UNAVAILABLE` when no verifier is configured, the provider is unreachable, or the route uses `pow`). In production, `vibe serve` and `vibe validate --deploy` refuse such routes until `VIBE_TURNSTILE_SECRET` and `VIBE_CHALLENGE_HOSTNAMES` are set.

- **Ownership (#53):** The implicit admin ownership bypass is removed. Models that need admin-wide access must declare `ownership: role(admin)`. `owner-key: id` is only allowed on user-like models.

- **Environment / slugs / pepper (#52):** Unknown `VIBE_ENV` values are treated as production. With PostgreSQL, unset `VIBE_ENV` is production. `--memory` is refused outside development. Outside development, `VIBE_API_KEY_PEPPER` is required (≥ 32 bytes). Missing, empty, or malformed `.vibe/slugs.json` fails closed (only `--memory` falls back to `slugs.example.json`).

- **Manifest path (#62):** `vibe manifest` without `-o` writes `./manifest.json` in the current working directory, not `<project>/manifest.json`.

- **Rate limits (#54):** Rate-limit keys follow the spec: a limit keyed by `account` or `input.<field>` must be paired with an `ip` limit on the same route, `family` is rejected until token refresh lands (#26), and only `per-minute` limits are accepted (1–10000). Behind a proxy, the client IP comes from forwarded headers only when the peer is a trusted proxy. `key: account` now means per-email (`input.email`), not per-tenant.

- **Request validation (#57), possibly breaking:** `vibe validate` rejects `## Request` fields whose type is not `string`, `integer`, `number`, `boolean` or `uuid`. At runtime, requests accepted before can now get 422: non-canonical uuids, query booleans other than `true`/`false`, empty required headers, non-object JSON bodies, and badly typed path params.

- **Route roles:** An empty `roles: []` list in a lock is a build error (`roles cannot be empty`); previously that form meant no role requirement. Callers who still want no role restriction should omit the `roles` field. A malformed `roles:` list (for example `roles: staff` without brackets) is also a build error.

### Changed

- **Product website:** Source moved from `site/` to `vibe-backend/vibe-backend.github.io`, which builds and deploys itself and reads this repo's `docs/` at build time. Removed the Pages workflow (`.github/workflows/pages.yml`) and `trigger-org-pages` dispatch (`ORG_PAGES_DISPATCH_TOKEN`).

- **Refresh tokens (#95):** Hardening of `_platform_refresh_tokens`: the runtime role gets SELECT, INSERT and UPDATE only on `used_at`, `replaced_by`, `grace_reissued_at`, `revoked_at` and `revoke_reason` (no DELETE); a `_platform_refresh_guard` trigger keeps identity columns immutable and revocation final; `vibe serve` verifies the grants and trigger per tenant at startup and fails closed. App SQL can no longer name `vibe_*` tables. Re-run `vibe migrate` for existing tenants.

- **Refresh tokens (#95):** `vibe migrate` now removes refresh-token families whose lifetime ended more than a day ago, in bounded batches (1000 rows per batch, at most 100 batches per run); live families are never removed. Refresh endpoint, policy settings and grace behaviour are documented in `docs/runtime-config.md`.

- **Refresh tokens (#95):** Hardening: when the refresh-token family lookup fails (for example a database or pool error), token refresh fails closed with a retryable 503 `SERVICE_UNAVAILABLE` instead of skipping the per-family limit. The presented token is not consumed.

- **Spec v1.8 D129 (docs, #147):** Specifies per-tenant DB roles (`tenant_<id>_rw`, `_public_reader`, `_public_writer`, migration-only `tenant_<id>_owner`), pool caps (5 per tenant and role, 15 per tenant, process-wide `VIBE_DB_POOL_MAX_TOTAL`, default 200) that return 503 `DB_POOL_EXHAUSTED` with `Retry-After: 1` immediately and emit `vibe_db_pool_exhausted_total{scope}`, a migrate-only-login owner role with UNIQUE indexes built inside the migration transaction, production credentials from a secret manager, and deploy-time comparison of compiled vs installed RLS policies. §2B.3 is an explicit allowlist: `ALTER COLUMN ... SET DATA TYPE`, `DROP TABLE`/`DROP COLUMN` (v1 has no deprecation flow) and unnamed non-UNIQUE indexes are rejected; an INVALID index the platform did not record is audited and alerted, never dropped; idle pools close after a fixed 5 minutes. The parser allowlist (#206), recorded-only INVALID-index drop (#207) and idle close (#165) are in #147. Backfill and replay cleanup run per tenant under FORCE RLS: each batch is a transaction where the migrate runner runs `SET LOCAL ROLE tenant_<id>_rw` (the migration role is a NOINHERIT member of the tenant's existing role), so the existing constant policies apply; parameterized, batched, and fail closed if `current_user` does not match. The migration role is the per-tenant owner role: NOLOGIN outside the migrate window, every SET ROLE audited, drift checked periodically, never a runtime login. Backfill may only do what `tenant_<id>_rw` is already granted; missing permission fails that tenant's backfill. Not yet implemented (#233). The owner's NOINHERIT membership in its own tenant's `tenant_<id>_rw` is the only membership the `vibe serve` startup check allows (granted `WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`, PostgreSQL 16+; exactly one such row per tenant, anything else fails startup); not yet implemented (#246). Backfill batches start with an explicit `BEGIN`, forbid savepoints, never use a shared pool, and check `current_user` and `session_user` before and after each UPDATE. Additional lock-validator hardening is in progress in #147.

- **Spec v1.8 D130 (docs, #132):** Specifies per-tenant and cross-tenant caps on new rate-limit counter slots per network (IPv4 /24; IPv6 /48 and /32), `VIBE_RATE_PLATFORM_FACTOR`, a 60 s fixed window with bounded LRU eviction, a 4,096-slot table per tenant (global budget `VIBE_RATE_EXPECTED_TENANTS` × 4,096; tenants under 64 slots always admitted), per-/24 and per-/32 platform tables of 4,096 entries each (platform pool = tenant budget + tenants × 64), `VIBE_RATE_PLATFORM_FACTOR` up to 100, fail-closed 429 when a table is full, and the `vibe_rate_limit_slot_refused_total{layer,reason}` metric (reason `network_cap`, `table_full`, `tenant_budget_exhausted`, `prefix_cap_exceeded`), and a hard memory cap `VIBE_RATE_TABLE_MEMORY_MAX_BYTES` (default 256 MiB, deliberately below the ~300 MB single-table worst-case estimate so the limiter reaches `table_full` first and fails closed; to be retuned after #195; memory measurement is a GA blocker, #195); #73's in-shard caps remain. Platform and memory tables reserve each tenant's 64-slot floor (memory reservation tenants × 64 × 3 KiB, 48 MiB at 256 tenants, at most half the cap); WARN alerts at most once per minute; the test IP override is enabled by `VIBE_HONOR_TEST_IP=true` in debug builds only; release builds ignore the header and refuse to start when it is set (#230; takes effect once #182 merges); v1 requires PostgreSQL 16+ and fails closed at startup on older versions (not yet implemented, #254); #195 measured ~481 B per slot (cap sized at 1 KiB per slot). Implemented in #182 except: the `rate_limit_active_tenants_high` alert (#234) and the `within_floor` distinction for `table_full` (#235), not yet implemented in #182. Residual risk (f), table_full within the floor when active tenants exceed `VIBE_RATE_EXPECTED_TENANTS`, accepted by the PM with these conditions; §4.3 documents raising `VIBE_RATE_EXPECTED_TENANTS` (max 4096) or `VIBE_RATE_TABLE_MEMORY_MAX_BYTES`.

- **Lock commit (#92, from #93):** Lock files from one compile are committed all-or-nothing through a journal; journal writes are atomic and recovery after an interrupted commit is hardened.

- **LLM_FORMAT_RETRIES (#92):** A value that is not an integer from 0 to 5 is an error instead of being silently clamped or ignored.

- **LLM errors (#62):** Failed LLM calls report the real HTTP status (only 401/403 blame the API key; 400, 404, 429 and 5xx are worded by status). HTML responses and 404s add a hint to check `LLM_BASE_URL` (OpenAI-compatible endpoints usually end in `/v1`). The message includes the request URL and the first 200 characters of the response; the API key and `key=`/`api_key=` query values are masked as `***` before truncation.

- **Rate limits (#54):** `VIBE_TRUSTED_PROXIES` accepts proxy IPs, CIDR blocks (v4/v6), hops with ports and IPv4-mapped IPv6; `X-Forwarded-For` is used only when the peer is trusted, taking the rightmost untrusted hop. IPv6 clients are bucketed per /64. `Retry-After` is the real time until the oldest hit leaves the window (quota: seconds until UTC midnight). Buckets are held in bounded, per-route/key-type LRU shards (10k each); at-limit buckets are never evicted, and a flood of one key type cannot block other clients.

- **Request handling (#57):** Authentication, role/scope checks and rate limiting now run before request validation, so unauthenticated callers get 401/403 instead of 422 details. Expression failures return a generic `422 Invalid request` (details go to the server log). Required headers are enforced case-insensitively; body, query and path values are type-checked. Early 400, 413 (payload too large) and 415 (unsupported media type) responses respect the route's `min_response_ms`.

### Security

- **JWT library (supersedes #144):** `jsonwebtoken` is upgraded from 9 to 11 with the `aws_lc_rs` backend (`default-features = false`, features `aws_lc_rs` and `use_pem`), so the `rsa` crate is no longer in the dependency tree. Building now compiles `aws-lc-sys`, which needs a C compiler (and CMake on targets without a prebuilt build path). The runtime JWT verifier rejects any configured algorithm other than ES256 and RS256. `sign-jwt` keeps supporting ES256 and RS256.

- **Browser refresh cookie (#78, spec decisions 141–148):** The spec adds to decisions 6, 45, 60, 61, 65, 72 and 101 for the httpOnly `__Host-` refresh cookie: login in cookie mode sets the refresh token only in `Set-Cookie`; `Max-Age` is the lesser of the remaining family and idle lifetimes; method, `Origin` and `X-Vibe-CSRF` checks run before the cookie is read (403 `CSRF_REJECTED`, cookie kept); cookie-mode logout with `scope: family` needs no access token: it must pass the refresh route's Origin allowlist and `X-Vibe-CSRF` (also in same-site mode), otherwise 403 `CSRF_REJECTED`; the token is read only from the `__Host-` cookie; it then always returns 204 and clears the cookie, revoking only that cookie's family in the slug's tenant, with D72 rate limits and minimum response time; fixed error codes (`INVALID_REFRESH_TOKEN` for both transports); cookie transport is opt-in per endpoint version. Spec only; refresh tokens and cookie transport are not yet implemented on main (see spec 4A.1b).

- **Cookie logout wording (#253, follow-up to #247):** Spec decision 147 and the 4A.1b error table now state that 401 `INVALID_REFRESH_TOKEN` with cookie clearing applies to refresh only; cookie logout returns 204 and clears the cookie (decision 145). Cookie logout required test 3 is split into (a) no cookie with only a body token and (b) a valid cookie plus a different body token, where only the cookie's family is revoked. Decision 145 (5), approved by PM on 2026-10-16: cookie logout applies only the D72 IP limit (30/min, counted as for refresh) and not the D72 family limit, an exception that applies only to cookie logout (refresh keeps the family limit); the 300 ms minimum response time is unchanged, and valid, invalid and missing cookies get identical 429s and response times. A new required test covers this. Spec only.

- **JWT signing algorithm policy (#198, spec decision 139):** The spec now fixes the `sign-jwt` and JWT verification policy: only ES256 (default) and RS256; RS256 keys must be at least 2048 bits and a shorter key makes startup/deploy fail closed; verification accepts only the one configured alg and rejects any other `alg` header, including `none`, HS* and the other of ES256/RS256; EdDSA is deferred to vNext. Spec only; parts are not yet implemented (see spec 4.1a).

- **Lock and manifest signatures (#167):** Signature verification uses `verify_strict`; weak keys and non-canonical signatures are rejected (#151). With lock signing removed in spec v1.8, this now applies to development manifest signatures only.
