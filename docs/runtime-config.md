# Runtime configuration

Moved from the README. Reflects the current source tree.

`--memory` is a dev executor. PostgreSQL needs two roles. `vibe migrate` connects with the owner role (`VIBE_MIGRATE_DATABASE_URL`) and grants SELECT, INSERT and UPDATE to the runtime role named in `VIBE_RUNTIME_DB_ROLE`. `vibe serve` connects as that runtime role (`VIBE_DATABASE_URL`, or `DATABASE_URL`) and refuses to start if the role is, or can `SET ROLE` to, a superuser or BYPASSRLS role, or can own any tenant schema, relation, function or type, because row-level security would not apply. The owner role needs `CREATE` on the database to create tenant schemas, but should have no `CREATE` privilege in any other schema (for example, revoke `CREATE` on schema `public`); it only creates objects inside its own tenant schemas. `VIBE_RUNTIME_DB_ROLE` is required:

```bash
VIBE_MIGRATE_DATABASE_URL=postgres://owner@db/app VIBE_RUNTIME_DB_ROLE=vibe_app \
  vibe migrate --manifest manifest.json --project tests/fixtures/shop --tenant tenant0001
VIBE_DATABASE_URL=postgres://vibe_app@db/app \
  vibe serve --manifest manifest.json --project tests/fixtures/shop
```

`vibe serve` uses a connection pool (`VIBE_DB_POOL_SIZE`, default 16). It waits up to `VIBE_DB_POOL_TIMEOUT_MS` (default 5000) for a free connection, and each request transaction runs with `statement_timeout` = `VIBE_DB_STATEMENT_TIMEOUT_MS` (default 5000). Connections to hosts other than localhost or loopback require TLS (certificate and hostname verified against the webpki roots) unless the URL says `sslmode=disable`. `sslmode=require`, `verify-ca` and `verify-full` always use verified TLS. `sslrootcert=<path>` trusts the CA certificates in that PEM file instead of the webpki roots (hostname is still verified), and `channel_binding=require` refuses to authenticate without SCRAM channel binding.

Structured markdown compiles with no model call. Natural-language sources need the variables in [.env.example](../.env.example). `LLM_*` wins over `OPENAI_*`. Sampling parameters are sent only for models in the adapter capability registry (`src/llm.rs`): Gemini 1.5 / 2.0 / 2.5 text models get `temperature: 0`, `topP: 1`, `topK: 1` and the seed (not tts, image, live or audio variants); OpenAI `gpt-5.1` / `gpt-5.2` get `temperature: 0`, `top_p: 1`, the seed and `reasoning_effort: none` (not `-pro`, `-codex` or `-chat` variants); OpenAI `gpt-4.1` / `gpt-4o` get `temperature: 0`, `top_p: 1` and the seed (not search, audio, realtime, transcribe or tts variants); exactly these Claude models get `temperature: 0` only (never together with `top_p`): Opus 4, 4.1, 4.5 and 4.6; Sonnet 4, 4.5 and 4.6; Haiku 4.5; Claude 3.7 Sonnet, 3.5 Sonnet, 3.5 Haiku, 3 Opus and 3 Haiku (each as the bare id or with a `-YYYYMMDD`, `-YYYY-MM-DD` or `-latest` suffix). Gemini 3 and later get none, because Google recommends the default temperature of 1.0 (lower values can loop). Every other Claude model (Opus 4.7 and later, Sonnet 5 and later, any newer Haiku, Claude 2.x) gets none; the newer ones reject non-default sampling parameters. A registered id must be followed by `-` or the end of the name, so `gpt-4.10` or `claude-opus-4-10` does not match. With `LLM_API_STYLE=responses` the seed is not sent. Other models and providers get none, and `vibe compile` warns. Set `LLM_SEND_SAMPLING=0` to send none even for registered models. Copy `.env.example` to `.env` (gitignored) and do not put a real key in the repo.

Local compiler endpoints: `LLM_ALLOW_PRIVATE_HOST=true` also allows named hosts
that resolve to non-public addresses (including fake-IP DNS proxies). This is
local development only and records private-endpoint locks. Use
`vibe validate --deploy --dev` and `vibe manifest --dev` to test these locks
locally with normal approval and signature checks. Both flags are refused in
CI and production. A signed dev manifest is accepted by `vibe serve` only in a
development run environment, including with `--memory`. Runtime environments
must still contain no `LLM_*` or `OPENAI_*` variables.

The runtime refuses to start when `LLM_*` or `OPENAI_*` is set. Public catalog reads resolve the tenant from `.vibe/slugs.json`. Only `--memory` falls back to `slugs.example.json` when that file is missing; otherwise public slug routes return 404. `VIBE_ENV` (case-insensitive) is development only for `dev`, `development`, `local` or `test`; `ci` is CI, and any other value is production. Unset counts as development with `--memory` and as production with PostgreSQL. Outside development, `--memory` is refused and `VIBE_API_KEY_PEPPER` must be set to at least 32 bytes (not characters); generate one with `openssl rand -base64 48`. The test fixture's [slugs.example.json](../tests/fixtures/shop/slugs.example.json) maps slug `acme` to tenant `acme0001`. Add another with `vibe slug add <slug> --tenant <id>`. Staff writes need a JWT (`VIBE_JWT_PUBLIC_KEY_PEM`, `VIBE_JWT_ISS`, `VIBE_JWT_AUD`, `VIBE_JWT_KID`). The PEM's algorithm is detected (ES256 or RS256); override with `VIBE_JWT_ALG` if needed. To use an identity provider's keys instead, set `VIBE_JWT_JWKS_URI` (https only — an `http://` issuer or JWKS URI refuses to start). Do not set PEM and JWKS together. If no PEM is set, the default is `{VIBE_JWT_ISS}/.well-known/jwks.json`. Keys are cached for 10 minutes, an unknown `kid` triggers a refetch at most once a minute (single-flight; other requests keep using the cache), and a failed fetch falls back to the old keys for at most an hour. For local JWKS experiments, point `VIBE_JWT_JWKS_URI` at an https endpoint that serves a static JWKS (a tunnel or a local reverse proxy with TLS); plain `http://localhost` is refused. `VIBE_JWT_ROLES_CLAIM` (default `roles`) names the roles claim (dotted paths like `realm_access.roles` are supported); a route's auth `roles-claim` overrides it. Reserved claims (`aud`, `scope`, …) are rejected. A route's auth block may also set `iss`, `aud` and `jwks-uri` (spec §4.1) to pin a different identity provider: `iss` and `jwks-uri` must be https, `jwks-uri` needs `iss`, and without `jwks-uri` the keys come from `{iss}/.well-known/jwks.json`. Route `iss`/`jwks-uri` hosts must be public: loopback, private, link-local (for example `169.254.169.254`), CGNAT and `.local`/`.internal` names are refused by `vibe validate` and at startup, with no development exception for lock values. Hosts are normalized before the check (one trailing dot stripped, lower-cased), so `localhost.` or `idp.internal.` are refused too, and names with an empty label (such as `localhost..`) are refused; IPv4-compatible, IPv4-translated (`::ffff:0:0/96`), discard (`100::/64`) and NAT64/6to4 IPv6 forms, site-local, multicast and reserved ranges are also refused. Only the env JWKS may point at a private host, and only with `VIBE_JWT_ALLOW_PRIVATE_HOST=true` in development; this applies both to `VIBE_JWT_JWKS_URI` and to the default `{VIBE_JWT_ISS}/.well-known/jwks.json` derived from `VIBE_JWT_ISS`. Limitation: the check looks at the URL's host as written. A public DNS name that resolves to a private address is not refused yet. Each URI gets its own cache, created at startup (an invalid one refuses to start); such a route accepts only its own issuer's keys and never falls back to the env keys, and an unreachable route JWKS returns 401. A JWT `scope` (space-separated string or array) or `scp` claim, and API-key scopes, are checked against the route's `scopes`; the caller must hold all of them. Empty route `scopes` means scopes are opt-in (not required). A malformed lock `roles:` or `scopes:` list (for example `roles: staff` without brackets) is a build error, never an empty allow-all. API keys are loaded from `VIBE_API_KEYS_FILE`: a JSON array of `{key_id, secret_hash, env, tenant_id, scopes, expires_unix, revoked}` records, where `secret_hash` is the HMAC of the secret with `VIBE_API_KEY_PEPPER` (see `hash_api_secret` / mint with a 12-char base32 `key_id` and `mbk_{live|test}_{key_id}_{secret}`). The file must be `chmod 600` and is re-read when its mtime changes (at most once a second); a bad reload keeps the previous keys. Keys are `mbk_live_…` when `VIBE_ENV` is production, and `mbk_test_…` otherwise. Auth failures return a generic 401; enable debug logging to see the operator-facing reason.

Per-IP rate limits and public-write quotas use the TCP peer address. Set `VIBE_TRUSTED_PROXIES` (comma-separated IPs or CIDR blocks, e.g. `10.0.0.0/8,2001:db8::/32`) behind a load balancer. `X-Forwarded-For` is honoured only from those proxies, and the rightmost hop that is not a trusted proxy counts. Hops may carry a port (`1.2.3.4:5678`, `[2001:db8::1]:443`), and IPv4-mapped IPv6 addresses count as IPv4. IPv6 clients are limited per /64. Rate and quota state is kept per route and key type with a fixed capacity; when a shard is full, its least recently used bucket is evicted, so flooding never blocks other clients. Buckets at their limit stay until their one-minute window ends, so each client network (an IPv4 address or an IPv6 /48) may create at most 100 active buckets per route and key type, and each wider network (IPv4 /24, IPv6 /32) at most 1,000; past that, only that network gets 429 for new keys. The last 1,000 of a shard's 10,000 slots are reserved for small clients: for IPv4, fewer than 5 buckets per address and fewer than 10 per /24; for IPv6, fewer than 10 new keys per /48 and fewer than 50 in total per /32. New clients usually still get in after heavy clients use up the rest, but this is a mitigation, not a guarantee. Clients sharing one address (CGNAT, or a proxy when `VIBE_TRUSTED_PROXIES` is unset) share that address's 100. A distributed client can still fill a shard and lock out new clients on that route, for example about 100 IPv4 /24s with 2 addresses each, or a few dozen IPv6 /32s (on top of the networks that fill the non-reserve slots); see [docs/release-hardening.md](release-hardening.md). Use load-balancer or CDN rate limiting as well. Saturated shards are logged as warnings.

## Refresh tokens

**Endpoint.** A route whose lock has a `### token-refresh` pipeline is the refresh endpoint. It must be public (no auth block) and takes `POST {"refresh_token": "..."}` (`transport: body`). A success returns `{access_token, token_type, expires_in, expires_at, refresh_token, refresh_expires_in}`; the returned `refresh_token` replaces the one sent, which stops working. Logout routes (`token-revoke`, `scope: family | all`) revoke the presented token's family or every family of the caller. Logout does not revoke access tokens already issued (they expire after their `ttl`, at most 1 h).

**Policy settings** (bullets of the `token-refresh` pipeline):

| Setting | Default | Limit | Meaning |
| --- | --- | --- | --- |
| `sign-method` | required | — | Method with a `sign-jwt` step that signs the new access token (`capabilities: [sign-token]`). |
| `refresh-ttl` | 30d | ≤ 30d | Family lifetime, counted from login. No token of the family works after it. |
| `idle-ttl` | 7d | ≤ 7d | An unused token expires this long after it was issued. |
| `reuse-grace` | 10s | 1s–10s | Window for one retry of the previous token (see below). |
| `transport` | `body` | `body` | Where the token travels. |

The manifest parser enforces these bounds before conversion to whole seconds, including rejecting `10.001s` and `10001ms`; this is not a database trigger check. Values outside these limits (for example `reuse-grace: 11s` or `0s`) fail `vibe validate` and the build, and `vibe serve` refuses to start with a manifest that carries one (spec §4A.1).

`refresh_expires_in` is the smaller of `idle-ttl` and what is left of the family lifetime. Rate limits: 30 requests per minute per IP (429) and 10 per minute per family; a `rate-limit` with `key: family` can only lower the family limit. Exceeding the per-refresh-family limit requires signing in again.

**Grace behaviour.** Every use rotates the token. Presenting a token that was already used normally revokes the whole family (also after the token expired). The exception: within `reuse-grace` of its first use, while the child it produced has not been used yet and the family is not revoked, the old token is reissued once. The unused child is revoked, a new child is issued in the same family, and the family lifetime is unchanged. A second retry, a retry after the window, or a retry after the child was used revokes the family. On PostgreSQL, rotation, reissue and revocation take a family lock, so concurrent retries resolve to exactly one reissue.

**Errors.** Unknown, expired, revoked and replayed tokens, and a missing or malformed body, all return the same 401 `INVALID_REFRESH_TOKEN`, padded to 300 ms. Refresh work has a 300 ms deadline measured from request start, and every refresh response uses the same request-start padding floor (at least 300 ms). Work that exceeds the deadline returns 503 `SERVICE_UNAVAILABLE`. If the token store cannot be read (for example the connection pool is exhausted) the refresh fails closed with 503 `SERVICE_UNAVAILABLE` and `Retry-After: 1`; the token is not consumed and can be retried.

**Storage and cleanup.** Only an HMAC of each token (key derived from `VIBE_API_KEY_PEPPER`) is stored, in `t_<tenant>._platform_refresh_tokens`, created by `vibe migrate` when a refresh route exists. The table has ENABLE + FORCE row level security with the same `tenant_isolation` policy as other tenant tables. App query roles (`public_reader`, `public_writer`, `app_rw`, `PUBLIC`) have no access; the runtime role gets SELECT and INSERT, and UPDATE only on the rotation and revocation columns (`used_at`, `replaced_by`, `grace_reissued_at`, `revoked_at`, `revoke_reason`); never DELETE, TRUNCATE or table-wide UPDATE. A `BEFORE UPDATE` trigger (`_platform_refresh_guard`) applies to every role, including the owner: `id`, `tenant_id`, `family_id`, `user_id`, `token_hash`, `parent_id`, `created_at` and the expiry columns never change, `used_at` is set once, and once `revoked_at` is set neither it nor `revoke_reason` can change (a revoked family cannot be restored). `vibe serve` checks these grants and the trigger for every tenant at startup and refuses to start on any difference (missing grant, extra column UPDATE, any DELETE, missing or disabled trigger); re-run `vibe migrate` to restore them. App SQL cannot name `_platform_*` or `vibe_*` tables. Revocation is an UPDATE. Rows are removed only by platform maintenance (`vibe migrate`, running as the tenant's table owner with a one-time migration credential), never by the runtime role: families whose lifetime ended more than one day ago are deleted, 1000 rows per batch and at most 100 batches per run, so a large backlog is cleared over several runs. Live families are never touched, so cleanup does not affect reuse detection. Run `vibe migrate` regularly (for example daily) to keep the table small. Policy decision (PM, #95): the runtime role reaches the table through the tenant's runtime login (`tenant_<id>_rw` once per-tenant roles land in #147; until then `VIBE_RUNTIME_DB_ROLE`), with the grants, trigger and startup check above. A dedicated refresh-store role is deferred to vNext (#250). The `--memory` executor removes finished families in bounded batches when a new family is issued.
